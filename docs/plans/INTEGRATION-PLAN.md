## 1. Judgement calls (decisions, not options)

**JC-1 Passwords: match bcrypt(cost 11) + pepper exactly. Non-negotiable.**
Existing customer hashes are bcrypt-of-(password+pepper) per `NVerseLaunchSequence1.java:150-160`. The scrypt reconstruction in `apps/api/src/auth/service/gatekeeper.service.ts` locks out every existing customer. Replace with `bcryptjs` (pure JS, no native build headaches; `bcrypt` native is acceptable if already compiled in CI — pick `bcryptjs` unless a benchmark shows login latency >250ms). Read the exact Java concatenation order (pepper prefix vs suffix, encoding) from `NVerseLaunchSequence1.java` before coding — do not guess.
*Verification without the pepper leaving the machine:* a local-only integration test (skipped unless `RUN_SECRET_TESTS=1`) that loads `AUTH_PASSWORD_PEPPER` from the local `.env`, takes one known password/hash pair from the local Postgres clone (a test account, or the dev creates one via the legacy hash function), and asserts `verify()` returns true. CI runs a pepper-independent unit test with a fixture pepper `"test-pepper"` and hashes generated by the same algorithm.

**JC-2 JWT: do NOT reproduce NVerseJWTService. Cut over to native tokens; recommendation: accept that legacy tokens die at cutover.**
The legacy library isn't in the repo; reverse-engineering its claim layout from decoded production tokens is days of work to preserve sessions that expire within `loom.config.jwt.token-validity` anyway. Cutover plan: at go-live, all clients re-authenticate once (frontends already handle 401 → login). Keep the existing HMAC-SHA256 implementation in `gatekeeper.service.ts` but: (a) sign with `nverse.jwt.secret` (mapped to `AUTH_JWT_SECRET`) so the secret at least matches infra expectations, (b) read TTL from `loom.config.jwt.token-validity` → `AUTH_JWT_TTL_SECONDS` instead of the guessed 24h, (c) replace hand-rolled encode/verify with the `jose` package (small, audited, no deps) — hand-rolled JWT is a security liability. **If the owner requires zero-relogin cutover**, the fallback is: decode a handful of live legacy tokens (header+claims are base64, not secret), replicate claim names, and verify signature with `nverse.jwt.secret` — budget 1 extra day, only do it if asked.

**JC-3 Payments: install official SDKs.** `stripe` and `razorpay` npm packages. Hand-rolling HTTP means hand-rolling webhook signature verification (HMAC timing-safe compare, Stripe's `t=`/`v1=` scheme, Razorpay's `order_id|payment_id` HMAC) — exactly where a subtle bug moves real money. SDKs give `stripe.webhooks.constructEvent` and `validateWebhookSignature` for free. Two deps for two money paths is the lazy correct choice.

**JC-4 Config: yes, `@nestjs/config` with a validated schema.** 10 files currently read `process.env` directly with no boot-time validation — that is the "silent 3am failure" machine. One `ConfigModule.forRoot({ validate })` with a zod schema (zod is likely already in the workspace; if not, `class-validator` is already a Nest dep — use whichever is installed, check `apps/api/package.json` first). Missing required secret ⇒ process refuses to boot with the *key name* (never the value) in the error. Details in §2.

**JC-5 The ~50 fake CRUD controllers: unregister, don't delete (yet).**
They write to nonexistent `commerce_*` tables and shadow real routes — they are live 500s/foot-guns. Cheapest safe move: remove `RestApiModule` (or the fake controllers) from the imports in `apps/api/src/commerce/rest-api.module.ts` / `commerce.module.ts` so they stop being routable, leave the files on disk for one release, delete in a follow-up once no frontend call hits a removed route (check access logs). Deleting 50+16 orphaned files now is a big diff that buys nothing the unregister doesn't; shadowing is the actual bug.

**JC-6 Scope cuts to afford the above:** WhatsApp (Freshchat), Zoho sync, AI/Gemini, and the notification fan-out get *config wiring + a kill-switch* but no new feature work this pass. They already have service skeletons; making them genuinely work is Phase 5, explicitly droppable. The `@ts-nocheck` cleanup (346 files) and orphan-file deletion are NOT in this plan — separate chore.

## 6. Risks, ranked

1. **Spamming real customers (highest consequence).** The clone DB holds real emails/phones. Any agent wiring SMTP/MSG91/WhatsApp against it can blast real people the moment code runs. Mitigations are structural, not procedural: flags default-false in the validated schema; allowlist enforced in code for `NODE_ENV!==production`; CI has no secrets; notification cron/queue processors must check the flag per-send, not per-boot. Agents C–F are forbidden from running any script that iterates customer rows with outbound side effects.
2. **Moving real money.** The workspace `.env` payment keys may be live. Key-prefix assertions + `PAYMENTS_LIVE_MODE` refuse-live logic ship *before* any provider call code (Agent D's first commit).
3. **Pepper/secret leakage.** Secrets only in git-ignored `.env`; error messages and logs name keys, never values; no secret in any test fixture, snapshot, or CI config; the mapping script prints key names only.
4. **Locking out customers via wrong bcrypt composition.** Pepper prefix/suffix/encoding must be read from `NVerseLaunchSequence1.java`, verified against a real clone-DB hash before merge. This is the one place "close enough" is a total outage.
5. **Legacy-token cutover (accepted, JC-2).** All sessions invalidate at go-live; frontends must handle mass 401 → re-login. Confirm with owner before Phase 1 merges; the fallback path is scoped.
6. **Email-encryption mismatch** silently corrupting new rows: round-trip against real ciphertext is a merge gate for Phase 2, not a nice-to-have.
7. **Stripe webhook raw-body**: classic Nest failure mode (body parsed before verification). Covered by the forged-signature test in Phase 3 exit criteria.
8. **S3 bucket blast radius**: dev-prefix + teardown deletes only objects the test created (by exact key).
