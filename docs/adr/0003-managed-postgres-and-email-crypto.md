# ADR 0003: Managed Postgres as system of record; email crypto at the boundary

- **Status:** accepted
- **Date:** 2026-07-23

## Context
Chosen over self-hosted Convex (single-machine, manual migrations) and raw AWS (operational burden).
Legacy stores `email` AES-encrypted at rest; passwords were never exportable from Loom's API.

## Decision
Managed Postgres (RDS/Neon/Supabase) — real FKs, `pg_dump`-portable, no paradigm lock-in.
Decrypt email only at the API boundary; never persist plaintext. Track auth-cutover secrets
(email key, JWT secret, OAuth) as infra config, not DB data.

## Consequences
- Data layer is swappable; business logic doesn't rewrite to change host.
- Cutover must supply the email-decrypt key + a password-reset/seed path (see runbook & the clone report).

## Status update (2026-08-12)

**No managed Postgres instance is wired yet.** `apps/api`'s Drizzle schema
(`database/schema/schema.ts`, `0000_dashing_xavin.sql`) was generated by introspecting a local dev
Postgres, not a managed RDS/Neon/Supabase instance — see `docs/ARCHITECTURE.md` §4 and §7. There is
a single snapshot migration and no incremental migration chain; treat the schema as a point-in-time
mirror, not a maintained source of truth, until re-introspected against whatever instance is
actually chosen.

**The email-decrypt-at-the-boundary design is also not wired.** `EMAIL_ENCODER_PORT` in
`commerce/cart/cart.module.ts` is currently bound to a no-op dummy rather than a real decrypt
implementation, so cart's tenant overview cannot decrypt an email through this port today — see
`docs/MODULE-MAP.md` §4. The decision to decrypt only at the boundary and never persist plaintext
still stands as the design; it has not yet been implemented against a real key.

Both blockers this ADR anticipated for cutover — a real managed Postgres, and a working
email-decrypt path — remain open. See `docs/runbooks/cutover.md` for the operational checklist.
